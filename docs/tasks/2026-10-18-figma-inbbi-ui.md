# 작업: Figma ‘인삐 UI’ 기반 캘린더·공지 UI 구현

상태: 계획 작성, Figma 파일 링크 대기

## 목표와 허용 범위

Figma ‘인삐 UI’를 디자인 기준으로 삼아 캘린더·공지 화면과 해당 화면에서 사용하는 아이콘을 Flutter로 구현한다. 디자인 확인 → 구현 단위 확정 → 코드 수정 → 자동 테스트 → 화면 비교 → 결과 기록을 각 단위마다 반복한다.

- 사용자 설명에 따른 페이지 구성: ‘캘린더 및 공지’, ‘아이콘’. 실제 페이지 이름·구성과 노드 ID는 아직 조회하지 않았다.
- UI 변경 허용 범위: 해당 Figma 페이지에서 확인한 캘린더·공지 화면과 두 화면에 필요한 아이콘. 모든 프레임을 자동으로 구현 대상으로 간주하지 않고 실제 화면·상태와 연결해 목록을 확정한다.
- 보존할 동작: 일정 조회·월 이동·날짜 선택·종류 필터·일정 추가/수정/삭제, 공지 검색·탭 필터, 계정 연결, 알림 배지·화면 이동, 840 논리 픽셀 반응형 기준.
- 범위 밖: 홈·강의·설정·로그인 UI, 앱 런처 아이콘, 서버·Google API 계약, 인증·알림 전송 방식 변경, Figma 원본 수정, Git 커밋·푸시.
- 공통 테마나 내비게이션 변경이 범위 밖 화면에도 영향을 주면 먼저 화면 전용 구성을 검토한다. 범위 밖 UI 변경이 반드시 필요하면 사용자에게 이유와 범위를 설명하고 승인을 받는다.

## 디자인 기준과 추적 표

현재 MCP는 파일 키를 요구하며 파일 이름만으로 파일을 찾는 도구는 제공하지 않는다. 파일 URL을 받으면 파일 키를 추출하고, 페이지 목록을 조회해 실제 페이지 ID와 구현할 프레임을 확인한다. 링크를 받기 전에는 디자인 수치·문구·아이콘을 추정하지 않는다.

| 디자인 대상 | 파일 URL / 페이지·프레임 ID | 읽기·시각 자료 | 대응 코드 | 상태 |
|---|---|---|---|---|
| 캘린더 기본 화면 | 미확인 | 미조회 | `lib/features/calendar/calendar_page.dart` | 대기 |
| 캘린더 입력·상세 상태 | 디자인에 존재하는지 미확인 | 미조회 | `calendar_event_dialog.dart`, `calendar_event_details_dialog.dart`, `calendar_date_picker_dialog.dart` | 대상 확인 필요 |
| 공지 화면 | 미확인 | 미조회 | `lib/features/notice_feed/notice_feed_page.dart` | 대기 |
| 위 화면의 아이콘 | 미확인 | 미조회 | 기존 Material 아이콘과 대조 후 에셋 경로·사용처 기록 | 대기 |

각 프레임을 읽을 때 URL, 노드 ID, 조회일, 원본 크기, 모바일/데스크톱 여부, 화면 상태, 스크린샷 위치를 이 문서에 기록한다. 실제 디자인 조회 후 프레임별 행을 추가하거나 나눈다.

## 기존 코드 조사

- 캘린더는 `CalendarPage`가 `BaseView`, `MonthCalendarGrid`, `CalendarWeekEventBars`, `NotificationBellButton`을 조합한다. 일정 동작은 `CalendarController`와 서비스에 위임한다.
- 공지는 `NoticeFeedPage`에 모바일/데스크톱 레이아웃, 검색과 탭 필터가 있다. 현재 화면 내 샘플 목록을 사용하므로 UI 작업을 실제 공지 서버 연동 완료로 표시하지 않는다.
- 재사용 후보: `AppColors`, `AppTextStyles`, `AppTheme`, `AppBreakpoints`, `MaxWidthBody`, `TitledCard`, `ResponsiveCardGrid`와 기존 달력·알림 위젯.
- `MainTabShell`의 캘린더 인덱스는 1, 공지는 2다. UI 적용을 위해 라우트·인덱스를 바꾸지 않는다.
- 기존 캘린더 서비스·입력·상세·날짜 선택·기간 표시 테스트를 재사용한다. 현재 공지 전용 테스트는 없어 검색·필터와 반응형 동작 검증을 추가할 예정이다.
- 저장소에는 기존 미커밋 변경이 많다. 작업 시작과 각 구현 단위 완료 시 변경 목록을 비교하고 기존 변경을 유지한다.

## 구현 순서와 완료 조건

### 1. 디자인 확인 및 구현 단위 확정

- [x] 기존 하네스 문서, 관련 화면·공통 위젯·테마·테스트 구조 확인
- [ ] Figma 파일 링크로 ‘인삐 UI’ 접근 및 실제 페이지 목록 확인
- [ ] 대상 프레임마다 디자인 컨텍스트와 스크린샷 확보
- [ ] 모바일/데스크톱, 기본·선택·빈 목록·오류·입력 상태 중 디자인에 정의된 상태 구분
- [ ] 프레임 → Flutter 위젯 → 검증 시나리오 대응 표 확정

`figma-design-to-code` 스킬을 사용한다. 최초 디자인 컨텍스트 조회에 스크린샷을 요청하고, 누락 시 별도로 확보한다. 응답이 불완전하면 화면에 보이는 하위 노드의 상세 정보를 확보한 뒤 구현한다. 이미 확인한 정보를 문서에 남겨 불필요한 재조회를 줄인다.

디자인에 한쪽 레이아웃만 있으면 기존 다른 쪽 레이아웃과 기능을 유지하고, 화면 폭에 따른 필수 배치 조정만 적용한다. 다른 쪽 화면의 새로운 시각 디자인을 임의로 만들지 않는다.

### 2. 아이콘·디자인 값 대응

- [ ] 실제 사용되는 아이콘만 기존 아이콘·에셋과 정확히 대조
- [ ] 원본 에셋이 필요하면 MCP 응답의 지침에 따라 내려받고 로컬 파일과 사용처 기록
- [ ] 에셋 등록, 실제 크기·비율·색상·선택 상태·접근성 이름 확인

아이콘 페이지 전체를 앱 전체에 일괄 적용하지 않는다. 캘린더·공지의 해당 위치에 사용되는 아이콘만 반영한다. 원본과 일치하지 않는 Material 아이콘으로 임의 대체하거나 디자인 스크린샷을 화면 이미지로 넣지 않는다. SVG가 필요한지는 실제 에셋을 확인한 뒤 결정하고 의존성은 필요한 경우에만 추가한다. 임시 Figma 에셋 URL을 앱 코드에 남기지 않는다.

### 3. 캘린더 화면 구현

- [ ] 확인한 캘린더 기본 프레임을 기존 공통 위젯을 활용해 구현
- [ ] 디자인에 포함된 입력·상세 상태만 범위 내에서 반영
- [ ] 기존 날짜 선택·월 경계·필터·완료 상태·일정 조작 동작 보존
- [ ] 관련 테스트와 모바일/데스크톱 화면 비교 완료

UI 변경이 서비스 동작을 바꾸지 않도록 한다. 필요한 경우 위젯 매개변수를 확장하되 기존 호출부의 기본 표현과 동작을 유지한다.

### 4. 공지 화면 구현

- [ ] 확인한 공지 프레임을 기존 반응형 레이아웃에 반영
- [ ] 검색·탭 선택·검색 결과 없음 및 목록 복귀 동작 검증
- [ ] 긴 제목·긴 검색어·좁은 화면의 잘림과 오버플로 확인
- [ ] 관련 테스트와 모바일/데스크톱 화면 비교 완료

정의되지 않은 상세 화면·서버 요청·일정 추가 기능을 UI 작업에 섞지 않는다. 기존 샘플 데이터로 검증하고 실제 연동 여부를 명시한다.

### 5. 전체 회귀 검증 및 마무리

- [ ] 수정한 Dart 파일에만 서식 적용
- [ ] `flutter analyze`와 관련 테스트 실행, 새 실패 없음 확인
- [ ] 전체 검증 실행 후 기존 실패와 이번 변경의 실패를 구분
- [ ] 각 프레임과 구현 화면을 비교하고 범위 내 차이 수정
- [ ] 실제 실행 명령·결과·스크린샷·남은 사항 기록

## 테스트와 화면 검증 계획

| 대상 | 자동 검증 | 화면 확인 |
|---|---|---|
| 캘린더 | 기존 `test/features/calendar/`, `test/core/widgets/calendar_week_event_bars_test.dart`, `test/widget_test.dart` 활용. 변경된 상호작용의 회귀 테스트만 보강 | 390·839·840·1280 논리 픽셀, 월/연 경계·종일·기간 일정·선택·필터 |
| 일정 입력·상세 | 대상 프레임에 포함된 경우 기존 dialog/date picker/actions 테스트 활용 | 저장·취소·수정·삭제, 긴 입력과 스크롤, 오류 시 입력 유지 |
| 공지 | `test/features/notice_feed/notice_feed_page_test.dart` 추가 예정. 검색·필터 조합, 결과 없음·복귀, 레이아웃 분기와 예외 확인 | 390·839·840·1280 논리 픽셀, 긴 제목·탭 줄·검색 필드 |
| 아이콘 | 위젯 테스트에서 접근성 이름·탭 동작 보존 확인. 에셋 파일 존재·등록·사용처 검토 | 프레임과 동일한 아이콘·위치·비율·선택 색상 확인 |
| 공통 영향 | 알림 이동·배지 및 변경한 공통 위젯의 관련 테스트, 이후 전체 Flutter 테스트 | 홈 등 범위 밖 화면의 기존 UI가 바뀌지 않았는지 확인 |

디자인 비교는 고정된 테스트 데이터·날짜·화면 크기로 진행한다. 필요한 경우 해당 프레임의 골든 테스트를 추가하되 최초 기준 이미지는 실제 Figma와 대조하고, 실패를 숨기기 위한 일괄 기준 이미지 갱신은 하지 않는다. 위젯 테스트 통과와 실제 렌더링 비교 완료는 별개로 기록한다.

예정 명령:

```sh
# 수정한 Dart 파일만 지정
dart format <수정한 파일 경로...>
bash tool/verify.sh calendar
# 공지 테스트 파일을 만든 후 실행
flutter test --no-pub test/features/notice_feed/notice_feed_page_test.dart
bash tool/verify.sh
```

공통 검증이 기존 서식 오류로 중단되면 파일을 기록하고 `flutter analyze --no-pub`, 관련 `flutter test --no-pub <경로>`, 전체 `flutter test --no-pub`를 별도로 실행해 분석·테스트 결과도 확보한다. 웹 에셋·의존성을 추가하면 `flutter build web`도 실행한다.

## 남은 사항

- 필요한 입력: Figma ‘인삐 UI’ 파일 URL. 파일 키·페이지·프레임 ID를 추측하지 않는다.
- 파일을 읽기 전이라 디자인 대응 표와 구체적인 시각 차이, 에셋 형식·개수는 미확정이다.
- 현재까지 앱 코드·UI·에셋·테스트는 변경하지 않았다. 링크 확보 후 1단계부터 이어서 구현·검증한다.
